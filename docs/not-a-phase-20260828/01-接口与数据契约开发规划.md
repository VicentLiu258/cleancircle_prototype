# 接口与数据契约开发规划

## 1. 目标与边界

本规划把 Onboarding、课程打标、月计划、周期更新和每日自适应落成一套可供 APP、管理后台、AI 服务和规则引擎共同使用的合同。

服务端必须保证：

- 安全规则由服务端执行，客户端不能通过改参数绕过 Hard Filter；
- User Training Profile、Course Profile、规则和结果均可版本追溯；
- Plan、Re-plan、Daily Adapt 的作用范围相互隔离；
- 预览与确认分离，重复请求幂等，并发修改可检测；
- 每个最终推荐都能说明保留、降级、替换或休息的原因；
- AI 输出不能未经校验/审核直接成为安全相关线上数据。

V1 不包含支付、会员权益、积分、社区评论和孕期自动排课接口。

## 2. 建议架构

前期不必拆成大量微服务，推荐采用“模块化单体 + 异步任务”，以清晰领域边界保留后续拆分能力。

```text
APP / Admin
    │
App API / Admin API（鉴权、DTO、幂等、权限）
    │
    ├─ Questionnaire & User Profile
    ├─ Course Profile & Review
    ├─ Recommendation Engine
    │    ├─ Priority / Hard Filter
    │    ├─ Plan
    │    ├─ Re-plan
    │    └─ Daily Adapt
    ├─ Check-in & Cycle Facts
    ├─ Audit / Explanation
    └─ AI Tagging Job Adapter
         │
         └─ Queue → AI Worker → Validation → Review Queue
```

推荐引擎以纯函数式领域核心实现：明确输入快照，返回候选、排除原因、决策和解释；数据库事务与消息发送放在外层应用服务。

## 3. 标准字段与枚举

### 3.1 命名原则

- JSON/数据库技术键统一 `snake_case`；
- 管理后台和 APP 的中英文文案来自版本化字典，不写死在规则中；
- 枚举只追加或弃用，不原地改变旧值语义；
- 时间使用带时区的 ISO 8601，业务日另存 `local_date` 与 `timezone`；
- 强度/负荷/风险值保留 `unknown`，不得把未知默认为低风险。

### 3.2 关键枚举

```text
fitness_capacity: L1 | L2 | L3 | L4 | L5
day_state: PUSH | SOFT | WARM
checkin_answer: FEEL_GREAT | ENERGY_LOW | PERIOD_STARTED
plan_change_type: KEEP | ADJUST | REPLACE | REST
decision_stage: PLAN | REPLAN | DAILY_ADAPT
review_status: DRAFT | AI_GENERATED | NEEDS_REVIEW | APPROVED | REJECTED | SUPERSEDED
risk_level: LOW | MEDIUM | HIGH | UNKNOWN
load_level: 1 | 2 | 3 | 4 | 5 | UNKNOWN
lifecycle_stage: REGULAR | IRREGULAR | HORMONAL_CONTRACEPTION | TTC | PREGNANT |
                 POSTPARTUM | PERIMENOPAUSE | POSTMENOPAUSE | PCOS | OTHER
```

Workout Type 与 Body Area 必须分开。建议正式字典至少包含：

- Workout Type：`STRENGTH`、`PILATES`、`YOGA`、`CARDIO`、`MOBILITY`、`STRETCH_RECOVERY`；
- Body Area：`FULL_BODY`、`CORE`、`LOWER_BODY`、`UPPER_BODY`、`GLUTES`、`BACK` 等。

`FULL_BODY` 不能再作为 Workout Type；“Gentle Strength”应表达为 `STRENGTH + 低负荷参数`。

## 4. 数据模型

### 4.1 字典与问卷

| 表 | 作用 | 关键字段 |
|---|---|---|
| `taxonomy_versions` | 标准字典版本 | id、status、effective_at、created_by |
| `taxonomy_terms` | 类型、部位、动作、风险原因等 | version_id、domain、technical_key、labels、value_type、deprecated_at |
| `questionnaire_versions` | Onboarding/复测版本 | id、type、status、schema_version、published_at |
| `questions` | 问题定义 | version_id、technical_key、input_type、sensitivity、required |
| `question_options` | 选项 | question_id、technical_value、labels、sort_order |
| `question_branch_rules` | 显示/跳过/Block 分支 | version_id、condition_json、action_json、priority |
| `profile_derivation_rules` | 回答到档案字段映射 | version_id、target_path、expression、safety_level |

发布时必须验证：技术键唯一、分支无死循环、必答可达、枚举存在、所有安全输入都有推导或 Block 结果。

### 4.2 用户档案与输入

| 表 | 作用 | 关键字段 |
|---|---|---|
| `onboarding_submissions` | 草稿/提交 | user_id、questionnaire_version_id、status、revision、submitted_at |
| `onboarding_answers` | 原始回答 | submission_id、question_key、value_json、answered_at |
| `user_training_profiles` | 不可变档案版本 | user_id、version、status、profile_json、effective_at、reason |
| `profile_field_sources` | 字段来源 | profile_id、json_path、source_type、source_id、rule_id |
| `profile_consents` | 敏感数据同意 | user_id、consent_version、scope、granted_at、revoked_at |
| `cycle_facts` | 用户确认的周期事实 | user_id、fact_type、local_date、source、supersedes_id |
| `daily_checkins` | 当天回答与确认 | user_id、local_date、answer、suggested_state、confirmed_state、revision |

原始问卷答案和派生档案分表保存。问卷版本改变时不改旧档案；只有新提交或明确迁移任务生成新档案版本。

### 4.3 课程档案与 AI 审核

| 表 | 作用 | 关键字段 |
|---|---|---|
| `course_profile_versions` | 不可变课程档案 | course_id、version、taxonomy_version_id、profile_json、review_status |
| `course_profile_values` | 可查询的规范化关键字段 | profile_id、field_key、numeric/text value |
| `course_tag_evidence` | 字段级证据 | profile_id、field_key、start_ms、end_ms、basis、confidence |
| `course_profile_reviews` | 审核记录 | profile_id、reviewer_id、decision、changes_json、reason |
| `tagging_jobs` | 批任务 | model_version、prompt_version、status、created_by |
| `tagging_job_items` | 单课程任务 | job_id、course_id、input_hash、output_profile_id、error_code |
| `model_runs` | 模型可追溯性 | model_version、input_hash、raw_output_uri、latency、cost |

### 4.4 计划与决策

| 表 | 作用 | 关键字段 |
|---|---|---|
| `recommendation_rule_sets` | 四阶段规则集 | stage、name、status |
| `recommendation_rule_versions` | 不可变规则版本 | rule_set_id、version、definition_json、effective_at |
| `training_plans` | 30 天计划版本 | user_id、version、profile_version、rule_version_matrix、start/end_date、status |
| `training_intents` | 每日训练意图 | plan_id、local_date、type、body_area、target_loads、status |
| `candidate_snapshots` | 当时的主备候选 | intent_id、rank、course_id、course_profile_version、score_parts、snapshot_hash |
| `recommendation_decisions` | 最终选择与解释 | stage、user_id、local_date、input_versions、result、reason_codes、trace_id |
| `replan_runs` | 未来重排任务 | plan_id、trigger_type、affected_range、status、new_plan_version |
| `daily_adapt_runs` | 当天自适应预览/确认 | checkin_id、original_course、result_course、change_type、status |
| `decision_exclusions` | 被排除候选 | decision_id、course_id、rule_key、reason_code、details_json |

`candidate_snapshots` 保存的是当次决策快照，不从最新 Course Profile 回算历史；否则历史解释会漂移。

## 5. APP API

建议统一前缀 `/api/v1/app`。以下为资源语义草案，最终以 OpenAPI 为准。

### 5.1 Onboarding 与档案

| 方法与路径 | 作用 | 关键约束 |
|---|---|---|
| `GET /onboarding/active` | 获取生效问卷与分支元数据 | 返回 questionnaire/taxonomy version |
| `POST /onboarding/submissions` | 创建草稿 | 支持 Idempotency-Key |
| `PATCH /onboarding/submissions/{id}` | 保存答案 | 必带 `If-Match: revision` |
| `POST /onboarding/submissions/{id}/validate` | 提交前校验 | 返回缺失/冲突/Block，不生成档案 |
| `POST /onboarding/submissions/{id}/submit` | 提交并生成档案 | 事务性冻结回答；异步生成计划 |
| `GET /training-profile` | 获取当前长期档案 | 可返回字段来源和用户友好解释 |
| `GET /training-profile/versions` | 获取版本摘要 | 敏感字段按权限裁剪 |
| `POST /training-profile/change-previews` | 预览修改影响 | 返回是否 Re-plan 及作用范围 |
| `POST /training-profile/change-previews/{id}/confirm` | 确认修改 | 新档案版本 + Re-plan job |

孕期分支建议返回结构化 Block：

```json
{
  "status": "blocked",
  "reason_code": "PREGNANCY_V1_BLOCK",
  "allowed_actions": ["EDIT_ANSWER", "VIEW_SAFETY_GUIDANCE"]
}
```

### 5.2 计划、日历和 Today

| 方法与路径 | 作用 |
|---|---|
| `GET /plans/current` | 当前 30 天计划摘要、版本和生成状态 |
| `GET /plans/current/days?from=&to=` | 日历日、训练意图、当前选择和变更标记 |
| `GET /today` | 今日聚合：周期上下文、Check-in 状态、课程、饮食/仪式内容 |
| `GET /recommendations/{decision_id}/explanation` | 个性化理由、命中规则、作用范围 |
| `GET /replans/{id}` | Re-plan 状态和前后差异 |
| `POST /replans/{id}/undo` | 在允许窗口内恢复上一计划版本 |

`GET /today` 不应在用户 Check-in 前推断“疲劳”；应返回 `checkin_status: pending` 和原计划课程。

### 5.3 Check-in 与 Daily Adapt

| 方法与路径 | 作用 | 说明 |
|---|---|---|
| `POST /daily-checkins/previews` | 提交一问并获取建议状态/调整预览 | 不写最终日程 |
| `POST /daily-checkins/previews/{id}/confirm` | 确认或修改状态 | 创建 checkin 与 adapt decision |
| `POST /daily-adapts/{id}/undo` | 撤销当天调整 | 受时间与完成状态限制 |
| `GET /daily-checkins/history` | 用户自己的状态历史 | 不暴露内部敏感推断 |

确认请求应包含 `confirmed_state` 和 `preview_revision`。若主计划或课程版本在预览后已变化，返回 `409 PREVIEW_STALE`，客户端重新预览。

### 5.4 周期事实

| 方法与路径 | 作用 |
|---|---|
| `POST /cycle-facts/previews` | 预览实际经期开始/结束对未来计划的影响 |
| `POST /cycle-facts/previews/{id}/confirm` | 写入用户确认事实并触发 Re-plan |
| `POST /cycle-facts/{id}/correct` | 用新事实纠正旧事实，保留 supersedes 链 |

周期预测与用户事实必须标明来源；用户事实优先，不覆盖原始记录。

### 5.5 课程与反馈

| 方法与路径 | 作用 |
|---|---|
| `GET /courses` | 按正式 V1 字段浏览课程库 |
| `GET /courses/{id}` | 课程客观属性与审核版本 |
| `POST /course-sessions` | 创建播放会话 |
| `POST /course-sessions/{id}/complete` | 完成/中断记录 |
| `POST /course-sessions/{id}/feedback` | 有用、太难、不适、其他反馈 |

反馈只能影响后续 History/质量信号，任何“喜欢”都不能覆盖 Hard Filter。

## 6. 管理后台 API

建议前缀 `/api/v1/admin`，延续现有鉴权与分页约定。

### 6.1 字典、问卷与档案推导

- `GET/POST /taxonomy-versions`
- `POST /taxonomy-versions/{id}/validate`
- `POST /taxonomy-versions/{id}/publish`
- `POST /taxonomy-versions/{id}/deprecate`
- `GET/POST /questionnaire-versions`
- `POST /questionnaire-versions/{id}/validate|simulate|publish`
- `GET/PUT /questionnaire-versions/{id}/profile-derivation-rules`

发布接口必须是显式动作，要求发布权限、变更说明和二次确认；已发布版本不可原地编辑。

### 6.2 Course Profile 与 AI 任务

- `GET /courses/{id}/profile-versions`
- `GET /course-profiles/{id}`
- `POST /course-profiles/{id}/review-decisions`
- `POST /tagging-jobs`、`GET /tagging-jobs/{id}`、`POST /tagging-jobs/{id}/cancel`
- `GET /tagging-review-queue`
- `GET /course-profiles/{id}/evidence?field_key=`
- `POST /course-profiles/{id}/publish`

批量发布前返回字段覆盖、未知值、高风险未复核和字典不兼容统计。

### 6.3 规则、模拟与审计

- `GET/POST /recommendation-rule-sets`
- `POST /recommendation-rule-versions/{id}/validate`
- `POST /recommendation-rule-versions/{id}/simulate`
- `POST /recommendation-rule-versions/{id}/regression-runs`
- `POST /recommendation-rule-versions/{id}/publish|rollback`
- `GET /recommendation-decisions`
- `GET /recommendation-decisions/{id}/trace`
- `GET /replan-runs`、`GET /daily-adapt-runs`

模拟接口只读，不写用户正式计划；生产用户数据默认脱敏，只有专门权限可按真实用户重放。

## 7. 异步事件

建议采用 Outbox 保证数据库提交与事件发送一致。核心事件：

| 事件 | 生产方 | 订阅方/用途 |
|---|---|---|
| `user_profile.version_created` | Profile | Plan/Re-plan、审计、分析 |
| `cycle_fact.confirmed` | Cycle | Re-plan |
| `daily_checkin.confirmed` | Check-in | Daily Adapt、分析 |
| `course_profile.approved` | Course Profile | 索引、候选池重建 |
| `rule_version.published` | Admin Rules | 缓存刷新、回归基线 |
| `training_plan.generated` | Plan | APP 通知、分析 |
| `replan.completed` | Re-plan | APP 差异提示 |
| `tagging_job.completed` | AI Adapter | 后台审核队列 |

事件必须含 `event_id`、`occurred_at`、`aggregate_id`、`aggregate_version`、`trace_id` 和 schema version；消费者按 `event_id` 幂等。

## 8. 一致性、并发与幂等

- 创建/确认类 POST 使用 `Idempotency-Key`，服务端保存请求摘要和首次响应。
- 草稿、预览和配置编辑使用 revision/ETag 乐观锁。
- 一个用户同一业务日只能有一个有效 Check-in；纠正产生新 revision，不覆盖审计。
- 同一用户同时只能有一个 Plan/Re-plan 写任务；新触发合并或排队，不能交叉覆盖。
- 课程档案发布与规则发布采用不可变版本；回滚是切换生效指针，不删除历史。
- 所有决策以输入快照计算；解释接口读取快照，不读取“当前最新值”拼接。

## 9. 错误码

建议错误结构：

```json
{
  "error": {
    "code": "PREVIEW_STALE",
    "message": "计划已变化，请重新确认",
    "trace_id": "tr_...",
    "details": {"expected_revision": 4, "actual_revision": 5}
  }
}
```

关键业务错误：

- `PREGNANCY_V1_BLOCK`
- `SAFETY_DATA_INSUFFICIENT`
- `NO_SAFE_COURSE_MATCH`
- `PROFILE_CONFLICT`
- `QUESTIONNAIRE_VERSION_EXPIRED`
- `PREVIEW_STALE`
- `PLAN_GENERATION_IN_PROGRESS`
- `UNDO_WINDOW_EXPIRED`
- `RULE_VERSION_INCOMPATIBLE`
- `COURSE_PROFILE_NOT_APPROVED`

这些错误必须在 APP 和后台有产品化状态，不能统一显示“网络错误”。

## 10. 安全、隐私与权限

- 生命周期、身体限制和周期事实按敏感数据处理；传输加密、静态加密、最小权限和访问审计。
- 营销标签与训练健康档案分库表/权限域；CRM 导出默认不包含敏感字段。
- 用户可查看数据用途、撤回可选同意、申请导出与删除；法定留存数据需明确说明。
- 管理员权限至少分为：课程运营、课程审核、规则配置、规则发布、敏感数据查看、审计员。
- 日志不记录原始自由文本、令牌和完整敏感档案；用 ID 和 reason code。
- 产品输出避免诊断/治疗表述；`Pregnancy Block` 是产品边界，不是医学判断。

## 11. 性能与可观测性

建议初始 SLO（评审后冻结）：

- `GET /today` P95 ≤ 500 ms（不含视频 CDN）；
- Check-in 预览 P95 ≤ 800 ms；
- 30 天 Plan/Re-plan 异步任务 P95 ≤ 10 s；
- 规则决策日志写入成功率 ≥ 99.9%；
- 所有线上推荐具有完整版本矩阵和 trace id。

监控至少包括：无安全课程率、Unknown 安全字段命中率、各 Hard Filter 排除量、Adapt 的 Keep/Adjust/Replace/Rest 分布、Re-plan 失败率、用户撤销率、AI 输出进入人审比例。

## 12. 开发分期与交付物

### 阶段 A：合同冻结

- 决策 D01–D12；
- taxonomy JSON、User/Course Profile JSON Schema；
- OpenAPI 初稿、错误码、事件 AsyncAPI/事件文档；
- 30–50 个跨端合同样例和规则 fixture。

### 阶段 B：档案与课程基础

- 问卷版本、用户档案、Course Profile、审核与字典 API；
- 数据迁移脚本、字段覆盖报告；
- 后台对应 CRUD/审核最小闭环。

### 阶段 C：推荐引擎

- Priority/Hard Filter、Plan、候选池；
- Re-plan、Daily Adapt、preview/confirm/undo；
- 决策日志、解释、回归 runner。

### 阶段 D：APP 接入与灰度

- Today、日历、问卷、档案、Check-in 和原因页接入；
- 压测、安全审计、数据一致性检查；
- 双写/影子决策、内测和小流量灰度。

## 13. 接口验收门禁

- OpenAPI lint、生成 SDK 与服务端实现无漂移；
- JSON Schema 覆盖所有正式枚举，未知值策略明确；
- 相同输入快照和版本得到确定性相同结果；
- Hard Filter 无匹配时绝不返回被过滤课程；
- Daily Adapt 测试证明只改今天，Re-plan 测试证明不改历史；
