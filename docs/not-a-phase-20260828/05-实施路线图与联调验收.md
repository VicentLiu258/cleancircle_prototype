# 实施路线图与联调验收

## 1. 路线图原则

四条开发线可以并行，但不能无合同并行。建议以“字典/Schema/OpenAPI/规则 fixture”为共同起点，以可验证的 Gate 决定是否进入下一阶段。

关键路径：

```text
D01–D12 冲突裁决
  → Taxonomy + Profile Schema + 规则输入输出冻结
  → Course Profile 数据就绪
  → Plan / Re-plan / Daily Adapt 引擎
  → APP/后台端到端联调
  → 影子运行与灰度
```

AI 批量打标、后台审核和服务端 Course Profile 可并行；APP 可以先用正式合同的 fixtures 开发，但不能以页面 mock 字段反向定义接口。

## 2. 建议里程碑

以下周数是常规团队的相对估算，用于排依赖，不是承诺日期。团队规模、课程素材质量和安全审核能力会直接影响周期。

| 阶段 | 参考周期 | 主要交付 | 退出条件 |
|---|---:|---|---|
| G0 需求冻结 | 1–2 周 | D01–D12 决策、V1 范围、标准术语 | 每个冲突有 owner 和唯一答案 |
| G1 合同冻结 | 2–3 周 | taxonomy、两类 Profile Schema、OpenAPI、事件、规则 fixtures | 四端评审通过，兼容策略明确 |
| G2 数据与基础服务 | 3–5 周 | 问卷/档案、Course Profile、AI 基线、审核后台 | Gold Set 就绪，上线课程可进入审核 |
| G3 推荐引擎 | 3–5 周 | Priority/Plan/Re-plan/Adapt、解释与审计 | 回归集和不变量通过 |
| G4 客户端与后台闭环 | 4–6 周 | APP 核心流程、规则模拟/发布、决策追踪 | 端到端场景通过 |
| G5 灰度发布 | 2–4 周 | 影子决策、迁移、监控、回滚、灰度 | 安全/隐私/性能门禁通过 |

G2–G4 中的子项目可部分重叠，整体建议预留 12–18 周形成可灰度的 V1，而不是把各阶段简单相加。

## 3. 各开发线依赖

| 开发线 | 可提前开始 | 必须等待的输入 | 关键输出给谁 |
|---|---|---|---|
| API/服务端 | 领域骨架、版本/审计基础 | D 决策、Schema、reason codes | APP、后台、AI |
| AI 模型 | 素材盘点、预处理 PoC | taxonomy、标签锚点、Gold Set | 课程审核、推荐候选池 |
| 管理后台 | 导航、通用表格/播放器 | OpenAPI、Schema、权限模型 | 运营、审核、规则发布 |
| APP | 导航、通用加载/错误组件 | OpenAPI、问卷/状态 fixtures、文案 | 用户体验、端到端验收 |
| QA | 测试框架、场景盘点 | 合同 fixture、不变量、版本矩阵 | 所有开发线 |

## 4. G0：需求冻结工作坊

参与人：产品、设计、课程/专业审核、算法、服务端、APP、后台、QA、隐私/安全负责人。

必须输出：

1. D01–D12 决策记录，尤其是 Pregnancy Block、盆底/核心压力字段、Yoga、类型字典和复测里程碑。
2. V1 范围与明确非目标。
3. 一张端到端术语图：User Profile、Course Profile、Priority、Plan、Re-plan、Daily Adapt。
4. 页面 SSOT 更新责任人：`design.md` 与 React 原型不能继续保留旧 12 题和错误规则。
5. 安全/隐私声明的审核责任和升级路径。

Gate：任何会改变 Hard Filter 输入或 Course Profile 安全字段的问题未决时，不进入规则开发。

## 5. G1：合同冻结

### 5.1 共同交付

- taxonomy 版本与中英文文案；
- User Training Profile JSON Schema；
- Course Profile JSON Schema；
- Onboarding 问卷 Schema、分支和推导规则；
- 四阶段规则输入/输出 Schema；
- OpenAPI 与错误码；
- 异步事件合同；
- reason code → 用户文案/后台文案映射；
- 最低客户端兼容和版本迁移策略。

### 5.2 合同 fixtures

至少建立以下可供所有端复用的 JSON fixtures：

- 普通 L2 用户、主目标减脂；
- L1 + 低跳跃耐受；
- 膝限制、腕限制、下背限制；
- 产后/盆底安全字段完整；
- 产后/盆底安全字段缺失；
- 孕期 Block；
- 不规则周期；
- 三种 Check-in 回答与三种用户确认状态；
- 有 Primary + A/B/C；
- Primary 被过滤但 Backup 可用；
- 所有候选被 Hard Filter；
- 周期事实提前触发 Re-plan；
- Profile 与 Check-in 同日变化；
- 旧版用户迁移。

fixtures 存在独立版本，服务端单元测试、后台模拟、APP Story/测试和 QA 自动化读取同一数据源。

Gate：Schema 和 OpenAPI 通过 lint，所有 fixtures 可由服务端验证器读取，前端生成类型无 `any` 漏洞。

## 6. G2：数据与基础服务

### API/服务端

- taxonomy、问卷版本、Onboarding 草稿/提交；
- User Profile 生成、版本和字段来源；
- Course Profile 草稿、审核、发布和查询；
- RBAC、敏感审计、Outbox 和异步任务框架。

### AI

- 标签指南、20–30 Gold Anchors；
- 预处理、结构化输出、Schema/一致性校验；
- 基线评估、任务 API 和审核路由。

### 管理后台

- B06 标准字典；
- B08–B10 问卷/推导；
- B03/B04 Course Profile；
- B07 审核队列和证据播放器。

### APP

- S03–S06 新 Onboarding、Block、档案摘要与异步计划壳；
- 老用户迁移页面；
- 统一 API client、错误状态和敏感埋点策略。

Gate：上线候选课程均有可审核 Profile；任何安全字段 unknown 都被明确路由，不能进入不受控候选。

## 7. G3：推荐引擎

建议按顺序交付：

1. Priority/Hard Filter 与 reason codes；
2. 30 天 Training Structure / Daily Intent；
3. Primary + Backup A/B/C 候选快照；
4. Re-plan 的范围和 Keep/Adjust/Replace；
5. Daily Adapt 的 Push/Soft/Warm 顺序；
6. 解释、决策日志、版本矩阵；
7. 预览、确认、撤销和并发控制。

必须自动验证的不变量：

- Safety 永远优先，unknown 策略不会放宽；
- Plan 不读取 Daily Check-in；
- Daily Adapt 只改今天；
- Re-plan 不改过去/已完成日期；
- PUSH 不自动升级；
- SOFT 先保持意图并降级，再换候选；
- 同日先 Re-plan 未来，再 Adapt 今天；
- 无安全候选返回 Rest/No Match，不绕过过滤。

Gate：冻结回归集 100% 通过，任一线上决策都能读取完整 trace。

## 8. G4：APP 与管理后台闭环

### APP 核心链路

```text
注册/迁移 → Onboarding → Profile 摘要 → 30 天 Plan
→ Today → Check-in preview → 用户确认 → Adapt
→ 播放/反馈
→ 周期事实 → Re-plan diff
→ 档案修改 → 未来计划更新
```

### 后台核心链路

```text
字典/问卷发布
课程 → AI 打标 → 证据审核 → Profile 发布
规则草稿 → 模拟/回归 → 审批发布
用户/日期 → 决策 trace → 候选与排除原因
```

联调时客户端只能使用服务端返回的 decision id 和原因；不得用本地 mock 规则补缺。

Gate：所有关键路径覆盖正常、Block、No Match、过期、重复、弱网和回滚场景。

## 9. G5：迁移、影子运行与灰度

### 9.1 数据迁移

- 旧课程标签映射到新字段时标记来源 `LEGACY_MIGRATION` 和低置信，未审核不进入安全候选；
- 旧问卷仅映射可确定字段，缺失安全信息要求用户补充；
- 旧计划只读归档，不用新规则回算历史；
- 新旧接口短期适配/双写，核对一致后再停止旧写入；
- 所有迁移可重跑、可校验、有失败清单，不直接覆盖源数据。

### 9.2 影子决策

新引擎在不影响用户的情况下读取相同输入，记录：

- 新旧结果变化；
- Hard Filter 差异；
- No Match 增量；
- 课程覆盖缺口；
- 性能与错误；
- 解释/版本日志完整性。

任何安全规则差异优先人工分析，不能只看课程点击/完成率选版本。

### 9.3 灰度顺序

1. 内部测试账户；
2. 课程/运营团队和明确同意的测试用户；
3. 小比例新用户；
4. 扩大新用户；
5. 老用户迁移分批开放。

灰度必须能按用户 cohort、客户端版本、规则版本和课程池版本停止；回滚切换生效版本，不删除新数据。

## 10. 端到端验收场景

| 编号 | 场景 | 预期 |
|---|---|---|
| E01 | 新用户完成标准问卷 | 生成 Profile v1 与 30 天 Plan，版本完整 |
| E02 | 用户选择孕期 | `PREGNANCY_V1_BLOCK`，无自动课程 |
| E03 | 膝限制 + 高膝负荷课程 | 候选被 Hard Filter，trace 有原因 |
| E04 | 用户感觉良好 | 建议 PUSH，默认 Keep，不自动升级 |
| E05 | 低能量 | SOFT 先降负荷/同意图 Backup，非直接无关换课 |
| E06 | 经期实际开始 | 周期事实确认；未来 Re-plan；今天独立 Adapt |
| E07 | 无安全候选 | Rest/No Match，APP 有明确状态，后台进入缺口统计 |
| E08 | 修改长期限制 | 新 Profile 版本，只调整未来，不改历史 |
| E09 | Check-in preview 后计划变化 | 确认返回 PREVIEW_STALE，重新预览 |
| E10 | 重复点击确认 | 幂等，只有一个 Check-in/decision |
| E11 | 同日 Profile 变化 + Check-in | 先 Re-plan 未来，再 Adapt 今天 |
| E12 | Course Profile 被回滚 | 新决策不用被撤版本，历史解释保持原版本 |
| E13 | AI 高风险低置信 | 进入人工审核，未批准不进候选池 |
| E14 | 旧用户缺安全字段 | 引导补充，不用默认值静默推荐 |
| E15 | 用户查看推荐原因 | 页面内容与 decision trace、实际课程一致 |

## 11. 发布门禁

### 产品与内容

- D 决策和 V1 非目标已签字；
- APP 与后台文案没有医疗承诺、羞耻化或压力型 streak；
- 无安全课程、孕期 Block 和不适反馈路径可用；
- Course Profile 覆盖上线课程，安全字段完成人审。

### 工程

- OpenAPI/Schema/生成 client 无漂移；
- 回归、集成、端到端和迁移测试通过；
- 幂等、并发、异步恢复和跨时区通过；
- 性能满足 SLO，队列和数据库容量有余量；
- Feature flag、版本切换、暂停和回滚演练通过。

### 安全与隐私

- 敏感字段加密、权限、访问审计和最小化采集通过评审；
- 日志、埋点、推送和错误上报不泄露周期/身体限制；
- 导出、删除、同意撤回流程通过；
- AI 输入不含用户敏感信息，视频资产权限和留存明确。

### 运营与可观测性

- 关键 Dashboard、告警、值班和升级联系人就绪；
- No Match、AI 审核积压、规则失败、任务超时有处置手册；
- 每次发布可定位 taxonomy、问卷、规则、模型和客户端版本；
- 灰度暂停条件和业务/安全阈值已配置。

## 12. 建议的项目台账

项目管理中建议持续维护五张表：

1. **Decision Log**：D 编号、选项、结论、owner、日期、影响文档。
2. **Contract Matrix**：字段/枚举在 Schema、OpenAPI、后台、APP、AI 的实现状态。
3. **Version Matrix**：taxonomy、问卷、Profile、规则、模型、客户端兼容关系。
4. **Coverage Matrix**：课程字段完整率、审核覆盖、用户场景与自动化测试覆盖。
5. **Risk Register**：安全漏标、无课、隐私、迁移、供应商和排期风险及缓解措施。

这五张表比按页面统计“完成百分比”更能反映项目是否真的可发布。
