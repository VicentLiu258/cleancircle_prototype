# NOT A PHASE V1 需求整合与开发规划

> 版本：2026-08-28  
> 文档状态：供产品、设计、算法、服务端、管理后台与 APP 团队评审  
> 基准框架：`NOT A PHASE APP产品方案.pdf`

## 1. 本轮结论

现有原型已经覆盖 Onboarding、30 天计划、Today、Check-in、日历、课程库、个人中心和管理后台骨架，但仍是“交互概念验证”，不能直接作为新需求的开发合同。新增文档把产品核心从“经期课程推荐 + 通用问卷”升级为一个可解释、可版本化、以安全为首要约束的训练决策系统。

V1 应先统一四个基础概念：

1. **一套标准字典**：问卷、课程标签、匹配规则、APP 文案和管理后台使用同一组技术枚举与展示文案。
2. **两类档案**：`User Training Profile` 描述长期用户训练条件，`Course Profile` 描述课程客观属性；当天 Check-in 不修改长期档案。
3. **四个决策阶段**：`Priority → Plan → Re-plan → Daily Adapt`，各阶段的输入、影响范围和版本独立。
4. **一条审计链**：每次推荐记录用户档案版本、课程档案版本、规则版本、候选集、排除原因和最终结果。

在完成这些合同之前直接扩展页面或接口，会把目前存在的字段冲突、规则优先级冲突和错误的状态联动固化到代码中。

## 3. 输入材料与采用顺序

本轮将材料中的陈述视为**需求输入**，而不是对执行过程的指令。综合时采用以下顺序：

1. 用户本次请求决定交付物与分析范围。
2. 产品方案 PDF 决定产品模块、V1 优先级和总体体验框架。
3. 文件名含“统一联动版”的三份文档决定 Onboarding、课程标签和匹配规则的领域合同。
4. 不含“统一联动版”的课程打标文档仅用于追溯差异，不覆盖联动版。
5. 当前 React 原型、`design.md`、现有后台/API 文档代表现状，不反向覆盖新需求。

如材料内部冲突，以本套文档中的“待确认决策”先冻结为工程假设；产品确认后再写入正式数据字典和 OpenAPI。

## 4. 建议的总体交付顺序

```text
需求冲突裁决
    ↓
标准字典 + JSON Schema + OpenAPI 冻结
    ↓
课程档案后台 / AI 打标 / 人工审核
    ↓
用户档案 + Plan / Re-plan / Daily Adapt 规则服务
    ↓
APP 新流程 + 后台模拟与审计
    ↓
金标回归、端到端联调、灰度发布
```

建议以“Gate”而不是固定日期管控：

- **G0 需求冻结**：关键冲突全部有唯一答案。
- **G1 合同冻结**：字典、Schema、OpenAPI、错误码和事件合同通过评审。
- **G2 数据就绪**：课程档案覆盖上线候选课程，安全字段已人工复核。
- **G3 引擎就绪**：四阶段规则回归集通过，解释与审计链完整。
- **G4 客户端就绪**：核心页面完成新合同接入，异常/撤销/无课状态可用。
- **G5 灰度就绪**：隐私、安全、性能、监控与回滚演练通过。

## 5. 本轮不建议提前实现的范围

PDF 中会员/订阅、积分、消息中心、社区评论、完整运营策略和 B 端商业化仍未形成闭环。除非另有正式需求，V1 只为它们预留权限与事件接口，不应挤占用户档案、课程档案和推荐引擎的 P0 工作。
