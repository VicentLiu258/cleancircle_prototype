# 综合差异分析与原型修改建议

## 1. 分析范围与基准

本分析以 `NOT A PHASE APP产品方案.pdf` 的产品结构为框架，将三份“统一联动版”视为新增领域需求，同时对照：

- 当前 12 页 `APP原型图修改.pdf`；
- React 原型中的移动端 S01–S34 与管理后台 B01–B57；
- 当前 `design.md`、后台 API、数据库和前端说明；
- 旧版 `NOT_A_PHASE_课程打标体系_V1.docx`。

新增文档中的流程、字段和规则只作为需求材料解释；本次真正执行的是用户提出的差异分析与规划文档交付。

## 2. 总体判断

| 层面 | 当前原型 | 新需求目标 | 结论 |
|---|---|---|---|
| 产品骨架 | 主要页面齐全 | 保留五 Tab 和 30 天计划骨架 | 可复用 |
| Onboarding | 12 题、含设备、通用目标 | 15 个主问题 + 生命周期/安全分支，产出长期档案 | 需重构 |
| 每日 Check-in | 已有一问和状态确认雏形 | 只影响当天；与周期、长期档案分离 | 可复用交互，需纠正规则 |
| 课程标签 | 通用难度、经期可用等扁平标签 | Course Profile A–E、证据、置信度、版本、审核 | 需重构 |
| 推荐 | 页面上呈现“智能调整” | Priority / Plan / Re-plan / Adapt 四阶段确定性规则 | 需重构核心 |
| 可解释性 | 少量自然语言理由 | 候选、排除、规则命中、版本可追溯 | 明显缺失 |
| 管理后台 | 页面骨架和通用 CRUD 较完整 | 配置、模拟、审核、发布、回滚、审计闭环 | 骨架可复用，领域模型需换代 |
| AI | 有课程打标 Demo | 多模态打标 + 金标集 + 人审；不直接做最终推荐 | 可扩展 Demo，需立项 |

一句话概括：**页面布局可复用，数据合同和决策语义不可沿用旧版。**

## 3. PDF 框架下的模块差异

### 3.1 用户进入与 Onboarding

PDF 要求新用户、老用户迁移、每日登录三条链路，并把轻量状态问题与 Push/Soft/Warm 状态确认放到核心体验中。新增问卷文档进一步把 Onboarding 明确定义为长期档案采集。

当前差异：

- S04 仍是 12 题，目标值包含“增肌/调理身体/改善心情”，与新主目标四值不一致。
- S04 最后询问设备，但统一联动版已取消用户设备问题，设备不参与主匹配和硬过滤。
- 缺少连续训练能力、跳跃耐受、受限部位、严重程度、生命周期和产后等必要分支。
- 缺少 `User Training Profile` 生成结果、版本、来源和后续编辑入口。
- 现有后台 B08–B10 采用问卷加权分和 14/28 天复测，和“结构化档案推导”不一致。

修改意见：

1. 将 S04 改为“15 个主问题 + 条件分支”的草稿式流程，支持断点续答；预计时间 3–5 分钟。
2. 提交前显示安全相关摘要；提交后生成长期训练档案，而不是长篇测评报告。
3. 新增档案维护页，允许用户修改目标、可训练时长、频次和健康限制；修改后生成新版本并触发 Re-plan。
4. 后台将“评分维度”改为“档案字段映射”，发布前做字典、分支可达性和安全约束校验。
5. 复测触发按 PDF 设置为 Check-in 里程碑 30/60/90/180/365 天及首次登录 90/180/365 天，并做后台可配置；不沿用 14/28 天常量。

### 3.2 Today 与每日状态

当前 S09、S19 已有一问 Check-in、系统推荐状态、用户确认/修改的两步结构，是最值得保留的部分。

当前差异：

- S09 将“经期第 1 天”直接等同 Warm Day，违反“周期只是上下文、当天身体状态优先”的规则。
- 未 Check-in 时已有“疲劳”预判文案，系统在用户输入前推断状态。
- 低能量替换直接从核心/力量变成拉伸，跳过“先降级再换课”，且未体现 Backup A/B/C。
- 现有设计文档仍保留能量、情绪、睡眠、不适等丰富 Check-in，与 PDF 的一题轻量体验不一致。
- 首 7 次解释、确认来源、规则版本和撤销行为尚未形成可验收状态机。

修改意见：

1. S19 保留一问：`Yes, I feel great / Energy is low / I got my period`，展示文案可本地化，技术值固定。
2. 先返回系统建议状态与原因，再由用户确认或改成 Push/Soft/Warm；确认前不落最终计划。
3. PUSH 默认保持，不自动升级；SOFT 先降冲击/负荷/跳跃，再尝试同意图备选；WARM 按温和化、换备选、休息的顺序执行。
4. `I got my period` 同时产生周期事实事件和当日 Check-in 输入，但不直接决定状态；周期事实可触发未来日期 Re-plan。
5. 所有调整提供“查看原因”和短时撤销；首 7 次额外展示状态机制说明。

### 3.3 30 天计划、日历与重排

PDF 与匹配规则均确认 30 天滚动计划，但新增规则把计划稳定性和每日自适应明确分开。

当前差异：

- S08 文案称 Check-in 会重排“今天和未来”，实际 Daily Adapt 只能改今天。
- S13/B13 用 Day1–28 或把每日状态写进月计划，边界不一致。
- 月计划中未建模 `Training Structure → Daily Training Intent → Primary + Backup A/B/C`。
- 经期实际开始后的未来计划调整没有明确“仅影响尚未发生且受影响的日期”。
- 缺少 Keep / Adjust / Replace 的变更类型和计划版本对比。

修改意见：

- Plan 阶段不读取当日 Check-in，生成 30 天训练意图和候选快照。
- Daily Adapt 仅覆盖今天的选择，不重写其余 29 天。
- Re-plan 只修改未来受影响日期，保留已完成、已跳过和不受影响的安排。
- 日历用颜色表达训练意图/状态时必须提供图例和文字，不以颜色作为唯一信号。
- 变更详情显示“原安排 → 新安排、原因、作用范围、版本、可否撤销”。

### 3.4 课程详情、播放与课程库

PDF 将课程库、播放、投屏与反馈列为可复用模块。新增标签体系要求课程详情同时承担解释责任。

当前差异：

- S10 展示“适用：黄体期/疲劳恢复”这类课程级结论，但新体系不定义周期阶段适用标签。
- S29 的难度、场景过滤依赖未进入 V1 标准字典的字段；设备虽可作为浏览元数据，但不能进入用户主匹配。
- 标签 Demo 中的卡路里/MET 不属于 V1 核心；`塑形` 被错误用作 Secondary Workout Type。
- 缺少局部负荷、风险原因、证据片段、审核状态和标签版本。

修改意见：

- 课程详情分开显示“课程客观属性”和“为什么今天推荐给你”；后者按用户和当天动态生成。
- 用户端只展示必要、易懂的信息；风险标签不做医疗结论，使用“训练限制/需要调整”语言。
- 课程库允许按时长、主类型、主部位筛选；设备仅作手动浏览元数据。难度/场景若未进入正式字典，不进入 V1 推荐接口。
- 播放完成后的“有用/太难/不适”等反馈进入 History 与质量监控，不直接绕过安全规则。

### 3.5 我的、连续记录与复测

当前 S25 强调连续天数/挑战，PDF 明确担忧它制造压力；S28 仍有“重新生成长报告”。

修改意见：

- 删除挑战式 streak 主视觉和“中断归零”文案。可保留私密的训练记录、累计完成数和非惩罚式回顾。
- S28 改为短问卷和档案变更摘要，不生成长报告；只有长期档案变化才触发 Re-plan。
- 在“我的”下新增训练档案、周期与隐私设置、推荐记录/原因、数据导出与删除入口。

### 3.6 社区、会员、积分与消息

PDF 对轻社区方向已有建议，但评论、审核机制、会员规则、积分、消息和运营策略仍未定稿。当前原型不应把这些模块与核心推荐一期强绑定。

建议：

- V1 社区若保留，只做内容浏览、发布和点赞；上线前必须确定内容审核与举报闭环。
- 会员、积分、消息只预留事件和权限点；收费不能影响安全过滤结果。
- 在 G1 合同冻结前，不为未决商业规则扩展推荐引擎分支。

## 4. 领域模型差异

### 4.1 User Training Profile

当前代码没有一个独立、版本化的长期训练档案。V1 至少应包含：

- 基础参考：年龄段、身高、体重、BMI 参考值；
- 目标：主目标、次目标；
- 能力：Fitness Capacity L1–L5、连续训练能力、跳跃耐受；
- 限制：部位、严重程度、用户描述、来源时间；
- 偏好：频次、时长、喜欢/避开形式；
- 生命周期：标准枚举与分支信息；
- 治理：`profile_version`、生效时间、字段来源、同意记录。

Daily Check-in 只能临时收紧当天选择，不能放宽长期限制或静默修改长期档案。

### 4.2 Course Profile

当前 `video_tags`/标签 Demo 不足以表达统一联动版。Course Profile 应按五组建模：

| 分组 | 核心字段 |
|---|---|
| A 身份 | Course ID、时长、主/次类型、主/次部位、设备元数据 |
| B 强度 | Overall、Cardio、Muscular、Impact Load，均为 1–5 |
| C 动作/负荷 | Jump Level/占比、姿势占比、关键动作、膝/腕/下背/肩负荷 |
| D 目标贡献 | 减脂、塑形、健康习惯、产后四项目标贡献 1–5 |
| E 风险 | 经期/产后风险等级与理由 |
| 治理 | 置信度、生成依据、证据片段、审核状态、纠正历史、版本 |

不能只保存“经期可用/膝友好”布尔值；它们会隐藏条件、证据和不确定性。

### 4.3 四阶段规则引擎

| 阶段 | 主要输入 | 影响范围 | 核心原则 |
|---|---|---|---|
| Priority | 全局规则 | 所有阶段 | Safety > Check-in > Goal > Capacity > Cycle > Preference > History |
| Plan | 用户长期档案、Course Profile、历史 | 未来 30 天 | 不读取 Daily Check-in；先结构和意图，再选主备课程 |
| Re-plan | 档案/周期事实变化、当前计划 | 未来受影响日期 | Keep > Adjust > Replace；不改历史 |
| Daily Adapt | 当天 Check-in、当天主备课 | 仅今天 | Push 保持；Soft 先降级；Warm 温和/替换/休息 |

当前 B11–B13 的单一优先级和排课器无法表达这四种不同作用域，应拆为可独立发布、回归和回滚的规则模块。

## 7. 现有技术文档的影响

现有 `admin-api-spec.md`、`admin-db-schema.md` 和 `admin-frontend-guide.md` 可以保留通用后台约定，但不能继续作为新领域的唯一合同：

- `video_tags` 需要迁移成版本化 Course Profile 与字段级证据；
- 通用 `quizzes/results` 需要补长期档案生成和字段来源；
- `schedule_rules` 需要拆分规则集、版本和四阶段执行记录；
- `user_schedules/day` 需要加入训练意图、主备候选和变更类型；
- `checkin_records` 需要 preview/confirm、状态来源、周期事实和撤销语义；
- 缺少候选快照、排除原因、推荐决策日志和全链版本矩阵。

建议新建领域表和接口，旧字段通过适配层读取；完成双写/核验后再迁移，避免一次性破坏当前原型。

## 8. 修改优先级

### P0：开发前必须完成
